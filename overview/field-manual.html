01 · The idea

Never accept an assertion a script can settle

Models, driven hard, do things you would not accept from a colleague: delete tests to make a suite pass, report work they did not do, write a task list no tool can parse, and loop one failing command a thousand times. Small local models did most of this in the early runs; a frontier model still graded broken code an A (section 05). Across many graded runs, every prose rule failed at least once and every deterministic gate held. So the rule is: if a script can check it, a script checks it, and the model does not get a vote.

Everything below is downstream of that one decision. The commands and agents are the ergonomics; the gates are the point. The CHANGELOG in the repository reads as a field log — every gate earned from a measured failure on a real run, with the deterministic check that stopped it.

02 · How it reaches the model

Three backends, one loop

Cloud is the default; Local is a resilience mode; Hybrid adds the GPU to the cloud loop. All three share every command, agent, and gate — only where the agent loop runs changes. Local-only was the naive starting point; it is not a pursuit any more.

Cloud default

The Ollama redirect is dropped; the loop runs on Anthropic (Sonnet / Opus / Haiku by alias).

GPU: RAG + vision, verified
install.cmd

Local resilience

Claude Code points at Ollama; the whole loop runs on the GPU with no network. For a disconnected afternoon: a datasheet-fed SoC/IC wiring plan, or a small Unity3D prototype from a one-page design doc. Not for large unattended builds.

GPU: the entire agent
install.cmd -Local

Hybrid opt-in

The cloud loop plus the GPU offered to the cloud model as a drudge co-processor via the local_generate tool.

GPU: RAG + vision + drudge
install.cmd -Hybrid

Division of labor in hybrid: cloud is the brain; the local GPU is senses (embeddings, vision) and drudge-work (implementation guesses, test data). local_generate is a separate tool registered only when the mode flag is set — in local/cloud it does not exist, so a model cannot be handed a job the mode exists to keep on the cloud brain. Its output is labelled [LOCAL DRAFT - verify before use].

03 · Context that persists

Precise-context RAG

The kit never re-sends the kitchen sink. Instead of loading whole documents into the window each turn, an agent asks for the specific passage it needs — a contract, a spec value, an exact API signature — and gets that, with a citation. Here is the whole path, index-time and query-time.

One index spans multiple roots (a ;-separated LOCALTOOLS_DOCS_DIR), so a shared reference corpus on another drive is searchable without copying it. The store is self-contained per project; .index is excluded from its own corpus so it never indexes itself.

Why this keeps the window clean

A frontier or local model asked to "use the design doc" will paste the whole thing every turn — and the important line drowns. RAG inverts it: the doc is indexed once, and each agent retrieves the one passage its step needs. Two structural pieces make the retrieval trustworthy rather than approximate:

API-SURFACE.md
A reflection pass writes the project's exact public signatures (annotated with their source .cs file) into the index, so a model retrieves real signatures instead of hallucinating a method that looks plausible.
Computed state
doc-stats -Findings derives the project's real status — task counts, coverage, ungrounded work — rather than letting the model narrate a status that isn't true. State is retrieved, not remembered.
The shell door
--search reaches the same index from any shell, even with the MCP server down. Across nine graded runs the models reached for the shell constantly and the MCP tool zero times — so the corpus grew a shell door.
Provenance
/research and dad corpus build cited, dated banks: every claim is grounded to a source with a fetch date, or it is not banked. A stale corpus is flagged, because outdated advice is worse than none.

04 · What holds the line

The deterministic gates

Each of these is a script the harness runs regardless of what the model decided — several are wired as Claude Code hooks so they fire at end-of-turn or before every tool call, outside the model's control.

close-unit
A unit is not "done" by assertion. The script builds it, runs the tests, confirms the tests actually ran (a green run of zero tests does not count), commits, and only then ticks the box.
the ratchet
Refuses a shrinking verification surface. One run rewrote a test file and 15 of 16 tests silently vanished; the suite went green. The ratchet blocks a close that has fewer tests than before.
loop guard
A PreToolUse hook that breaks a command / search spiral. One run repeated a single search 1023 times; another looped a shell probe 920 times.
dad-guard
A Stop hook: a turn cannot end on uncommitted code that nothing has built or tested. Every earlier gate was model-invoked; this one the model cannot decline.
env-block detector
When Windows App Control / WDAC refuses to run a build, the kit STOPS and reports it — and forbids agents from disabling your security to get past it (a real run tried).
dad watch
A no-progress alarm: git HEAD frozen while the disk is busy is the signature of a spiralling subagent. It makes hours of silence loud in minutes.
secret scanner
A pre-commit hook scans for credentials before anything reaches git or the RAG index; a hit aborts with nothing written.

05 · Field evidence

What the gates caught that the model missed

Figures in this section come from the author's run log of the cms3 build; the transcript is not reproduced in this repository. From the cms3 run of 2026-09-15 — on a frontier cloud model, which sharpens the point. The model wrote plausible code and graded its own stories generously (A / A / B). A deterministic close on every unit (it ran 111 times), plus a full /audit that reads real code and issues live HTTP instead of trusting a checked box, found user-facing defects that green tests had hidden. The run was clean — 68/70 tasks, 11/13 stories, no spiral — and these still surfaced:

S1 · Delete that never deletesA → B−

Graded A, tests green. The admin view issues hx-delete (a raw HTTP DELETE); the controller maps only [HttpPost] — so clicking Delete returns 405 and the page is never removed. The lone "delete" test asserts the confirm-string appears in the HTML; it never issues the request or checks the row is gone. Caught by reading the code and a live curl (405 confirmed) — a green test masking a dead feature. Filed as S12.

S4 · Upload wired to an API that doesn't existA → C

Graded A on a feature that couldn't even be constructed. The original A was given while IImageUploadService was never registered in DI — the controller could not be instantiated, the feature was unreachable end to end. After that was fixed, the re-audit found the Quill imageUpload module is an invented API: Quill ships no such module, so getModule('imageUpload') returns undefined and throws a TypeError in a real browser — the uploaded image never reaches the editor, and a placeholder alert() shipped in its place. Caught by grepping for the Quill.register that has to exist and finding none. Filed as S13.

S5 · A confirmation modal dead on arrivalB → C

Graded B, "all functional" — unverified against runtime. The purpose-built modal is called as showConfirmationModal(msg, onConfirm, onCancel) but defined as (message, element), so it reads element.dataset.deleteUrl off a function and throws before the modal is ever shown; a second undeclared variable is a latent ReferenceError. The toast handler is wired twice (byte-identical), so every notification fires two. Caught by reading the call site against the definition, not the checkbox.

Supporting deterministic catches the same run surfaced: a design doc that said Tailwind while the app was built on Bootstrap (doc-vs-reality drift, reconciled); a home page missing its Bootstrap CSS link; stories marked DONE with acceptance boxes still unchecked and code-verified unmet; an unclosed HTML comment hiding the Domain-model section from rendering; and two security dependency fixes pinned with ADRs. None of these were things the model flagged — they are things a script or a read-the-real-code discipline settled.

06 · Components & dependencies

What it's built from

A set of global Claude Code commands, agents, hooks, and PowerShell gate scripts, plus one small C# MCP server. No fork of Claude Code, no second server, and no service of its own that your code is sent to (in Cloud and Hybrid the model provider still sees what the model sees).

local-tools
The one C# MCP server (net8.0, RollForward=LatestMajor). Tools: index_datasheets, search_datasheets, list_datasheets, ingest_url, web_search, describe_image, detect_objects, transcribe_audio — plus local_generate in hybrid.
Runtime deps
Windows 10/11 · Ollama (local/hybrid; verified-optional in cloud) · Claude Code CLI (Node) · .NET 8+ SDK · git. Optional: VS Code + extension, uv (voice / transcription), an NVIDIA GPU (tuned on a 16 GB RTX 5080).
C# libraries
ModelContextProtocol · PdfPig (PDF text) · AngleSharp (HTML) · System.Numerics.Tensors (SIMD cosine) · ONNX Runtime + SkiaSharp (object detection) · MetadataLoadContext (signature reflection).
models.json
Single source of truth: alias, -cc variant, base tag, role, VRAM, and the cloud id per model. sync-models generates the Modelfiles (raising num_ctx); install / uninstall / doctor all read it.
The install
install.ps1 detects its own location, reconciles Ollama, builds the server, installs global commands/agents + settings.json (paths auto-fixed), puts dad on PATH. dad doctor reports readiness and the active mode.

07 · What it's for

Workflows & honest limits

The loop is design-doc-driven: /scaffold → /design → /stories → /taskmap → /build, with /assess and /document for brownfield adoption, /research and /corpus for grounded knowledge, and /audit, /grade, /retro for review. Good fits: C#/.NET services and web apps, Python apps and data pipelines, research projects with a document corpus and datasets rendered as a site.

▮ Does well

  • Turns a vague idea into a locked design doc, then stories, then a task map, then built & tested units.
  • Reverse-engineers a brownfield codebase into a cited, prioritized assessment (/assess).
  • Precise, cited retrieval from a project corpus — specs, signatures, prior research — without context bloat.
  • Keeps any model honest: no phantom "done", no shrinking test surface, no thousand-call spiral.
  • Runs the identical gates on cloud, hybrid, or — for small jobs when the network is gone — local.

▮ Limited at

  • A full /design → /build → close has not completed on a local model without human repair. That is why Local is a resilience mode, not the headline.
  • Pixel-level visual taste. There is no exit code for taste; the UI loop reviews behavior and screenshots, not beauty.
  • Hard reasoning at the local tier — the local model is the ceiling; Cloud is the default for that reason.
  • GitHub Copilot CLI as a second harness is a pilot, measured once against one version — unverified, not a supported target.
  • Windows-only by design (PowerShell + .cmd); cross-platform is a deliberate post-1.0 question.

08 · Where this sits

The field, honestly

DrDad's three ingredients — a spec before code, a verifier that checks real correctness, and persistent context across sessions — are the shape people have started calling "loop engineering". That is a 2026 label used in blog posts and guides about the agent loop Andrej Karpathy published as autoresearch: a human-edited program.md as the spec, a fixed five-minute budget, and a numeric verifier (val_bpb) the agent cannot grade for itself. No source I found has Karpathy using the phrase himself, so the credit goes to autoresearch for the loop and to the write-ups for the label. DrDad is one working implementation of that shape for coding, with the enforcement done by scripts instead of instructions.

What it isRelation to DrDad
claude-gatesInstallable deterministic hooks for Claude Code that block or warn when a tool call breaks a rule (DevRik99; MIT)Independent, same conviction: enforcement lives outside the model
claude-code-audit-gateAn independent audit agent that never writes code, re-verifies every fix, and gates the release with hooks, pre-commit and GitHub Actions (fotografvecerek-ai; MIT)Independent, same conviction, different mechanism: an auditor rather than in-loop gates
BMAD-METHODAgentic planning: personas, templates, context-engineered story files (MIT)State of the industry for planning. DrDad is the guard layer under it, not a rival

The one real disagreement. claude-gates ships a no-coauthor gate that blocks a commit carrying an AI or agent attribution trailer (Co-Authored-By and similar); it is enabled by default and can be overridden per commit or in config. DrDad goes the other way: AI attribution is required, and the commit trailers are how this repository's own history says which changes were AI-assisted. A guard layer that makes agents prove their work should not also make the authorship harder to see.

BMAD is the planning layer; DrDad is a guard layer that any methodology can run on top of — "BMAD on DrDad", not "versus". Run the method for its planning rigor, on a substrate that will not let a model quietly cheat. The convergence with the projects above is the reassuring part: several people arrived at the same shape independently.

09 · Where this came from, where it goes

Roadmap

Two intertwined stories: DrDad the harness, and cms3 the proving-ground app whose real failures earned most of the gates. Forward stages are directional, not commitments.

▮ DrDad — the harness

Hardened failure by failure into a field log; each gate is a scar with a test.

Where it started
  • A local-only kit (the naive starting point): Claude Code redirected at Ollama, one C# RAG server, a design/proto/spec/build loop.
  • The core gates from real disasters: close-unit, the ratchet, the loop guard, dad-guard.
Where it is (v0.59)
  • Integrity-aware state, exact API surfaces, domain grounding, research provenance, corpora, brownfield /assess.
  • Cloud is the default; local is kept as a resilience mode; hybrid adds the GPU to the cloud loop. 278 checks in the kit's own suite, 0 failed.
  • The design doc is reconciled with the cloud-first mission (S28), and the installer follows it (S29): no flag installs Cloud, -Local is the explicit Local switch, and a no-flag re-run keeps an installed Local or Hybrid mode.
  • GitHub Copilot CLI as a second harness: a pilot, unverified.
Where it can go
  • A library of authoritative UI "skins" as corpora; wider stack templates; cross-platform after 1.0.
  • Autonomous routines — the loop that grounds and re-grounds itself unattended.

▮ cms3 — the proving ground

An ASP.NET Core CMS built by the loop; its stumbles are the kit's curriculum.

Where it started
  • A local /design → /build run: real controllers, EF Core migrations, integration tests — 15 of 44 tasks before a Windows policy blocked test execution.
Where it is
  • Latest cloud run: 68/70 tasks, 11/13 stories, no spiral — and a full /audit re-graded four "done" stories (S1, S4, S5 down; S2 refined) by live-verifying, filing two real follow-ups (S12/S13).
  • Proof the kit was sound and that the gates earn their keep even on a frontier model — the local model was the ceiling, not the method.
Where it can go
  • A clean completion to a running, migrated, secured app.
  • Real UI through the razor-htmx-ui skin corpus, reviewed logged-out and in.
