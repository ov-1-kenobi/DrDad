after closing S4 (R35 sandboxing) and S5 (DAD-kit -> DrDad rename). Depth note: this is a single-pass,
tool-assisted review (Grep + direct script execution to reproduce claims), not an exhaustive line-by-line
audit of all ~11k LOC of PowerShell/C#. Every finding below was either read directly at the cited line or
reproduced by running the actual script/test - none are inferred from names or comments alone. No
`search_datasheets` SME corpus citations appear because DESIGN.md's own header states
`Security review: NOT-REQUIRED (local-only dev CLI; no auth, no user data stored, no exposed service)` -
this is a dev-tooling repo, not a service with an attack surface a security corpus would meaningfully speak
to. Findings are instead judged against the kit's OWN stated contract (`CLAUDE.md`, `docs/DESIGN.md`,
`.gitattributes`) and cross-checked by actually running `test-kit.ps1`.

## Architecture

Three cleanly separated layers, exactly as `CLAUDE.md:6-10` and `docs/DESIGN.md:377-393` describe:

- **`local-tools/` (C# MCP server)** - stdio server, one process, `RollForward=LatestMajor`
  (`docs/DESIGN.md:47`). Exposes RAG (`search_datasheets`, `index_datasheets`), web (`ingest_url`,
  `web_search`), and sensor tools (`describe_image`, `detect_objects`, `transcribe_audio`) per
  `docs/DESIGN.md:47-51`. This is the only code the kit ships as a compiled binary; everything else is
  interpreted (PowerShell/Markdown), which is a deliberate seam - `CLAUDE.md:51` ("one C# server only").
- **PowerShell orchestration layer** (root `*.ps1` + `.cmd` wrappers) - this is where almost all the
  kit's actual logic lives: `close-unit.ps1` (unit close-out, 576 lines), `ratchet.ps1` (verification-surface
  shrink guard, 227 lines), `doc-stats.ps1`, `install.ps1`, `new-project.ps1`, `upgrade-project.ps1`,
  `test-kit.ps1` (the gate itself, ~4,100 lines). These scripts are heavily interdependent by direct
  invocation (`close-unit.ps1:266-268` shells out to `api-surface.ps1`; `close-unit.ps1:358-360` shells out
  to `ratchet.ps1`; `close-unit.ps1:244-245` shells out to `free-locks.ps1`) rather than through any shared
  library - each script re-implements its own file I/O, JSON handling and error-shielding. This is the
  primary architectural seam: a convention change (e.g. "how do we write a text file") has to be applied
  N times by hand across N scripts, which is exactly the bug class in Top Issues #1-#3 below.
- **Markdown layer** (`global/commands`, `global/agents`, `templates/`) - the actual "modes" (`/design`,
  `/build`, `/assess`, etc.) and the 20+ agent personas are prose files, installed verbatim into
  `%USERPROFILE%\.claude\` by `install.ps1`. This layer is validated only structurally by `test-kit.ps1`
  (frontmatter names match filenames, referenced agents exist, Task tool named) - never semantically, which
  is appropriate since it is prose consumed by a model, not code.

**Data flow for the "self-hosting" case this assessment was requested about**: this repo IS also a DrDad
"project" (has `docs/STORIES.md`, `docs/TASKS.md`, `grades/`), so `close-unit.ps1` runs against its own
`CLAUDE.md`/`docs/` when a unit closes here. That dual role (kit AND dogfood project) is exactly why the
CLAUDE.md-shape gap in Top Issue #2 went undetected for as long as it did - `test-kit.ps1` tests
`close-unit.ps1`'s behavior against synthetic fixture `CLAUDE.md`s (all correctly shaped, e.g.
`test-kit.ps1:1317`), never against the kit's own root `CLAUDE.md`.

**Coupling note**: `close-unit.ps1` is the most central node - it is invoked at the end of every task/story
and itself invokes `api-surface.ps1`, `ratchet.ps1`, `free-locks.ps1`, and `local-tools.exe --reindex`
(`close-unit.ps1:266-268,358-360,244-245,433-438`). A regression in any of those four is invisible until a
close-unit run, which is also the only place several of them are ever exercised outside `test-kit.ps1`
fixtures - which is exactly how the API-SURFACE.md CRLF bug (Top Issue #1) went unnoticed: it only fires on
a real build+close, and no fixture in `test-kit.ps1` regenerates a real `docs\API-SURFACE.md` through the
real `api-surface.ps1` post-processing path against a `.gitattributes`-governed tree.

## Security

`docs/DESIGN.md:2` explicitly scopes this: `Security review: NOT-REQUIRED (local-only dev CLI; no auth, no
user data stored, no exposed service)`. Consistent with that stated risk posture, findings here are modest:

- **Secret hygiene is a real, tested control.** `scan-secrets.ps1` is wired as a pre-commit hook
  (`install-hooks.ps1`) and has dedicated `test-kit.ps1` coverage (patterns for AWS/GitHub/Slack/Google/
  Anthropic/OpenAI/Azure/PEM/JWT, `test-kit.ps1:1205-1250`), including a documented allowlist escape
  (`# DAD-ALLOW-SECRET`) and negative tests that a bare placeholder like `<your-password-here>` does NOT
  false-positive (`test-kit.ps1:1237`). No gaps found in this pass.
- **Shell-out surface is intentionally broad but consistently guarded.** `close-unit.ps1`'s `Invoke-Verify`
  (`close-unit.ps1:55-62`) never uses `Invoke-Expression` and documents why not (`close-unit.ps1:54`: "a
  string containing 'exit' would kill us"). A repo-wide grep for `Invoke-Expression`/`iex ` across all
  `.ps1` files found zero live call sites - only that one comment explaining the avoidance. The command
  string it runs comes from the PROJECT's own `CLAUDE.md` (human-authored), not from model output or
  network input, so this is intentional-by-design command execution, not injectable surface.
- **The one real, already-known and already-mitigated risk class is "self-verification touching real
  machine state,"** which is exactly what R35 (`docs/DESIGN.md:357-375`) and this session's S4 close were
  about: verifying an uninstall/teardown acceptance criterion against the REAL `~/.claude`/PATH/env instead
  of an isolated target. That gap is described as closed by S4/T4.1-T5.1's grade cards
  (`grades/S4_GRADE.md`); I did not re-audit the fix's completeness as part of this pass (out of scope -
  already graded this session).
- **No SME/security-corpus citations are used here** because there is no `search_datasheets`-indexed
  security corpus loaded for this pass, and the design doc's own posture (local-only CLI) is the correct
  bar to judge against rather than a web/service security checklist (OWASP Top 10 etc. would be a category
  error for a tool with no network listener and no multi-tenant data).

## Implementation

- **Convention drift risk: no shared "write this text file correctly" helper.** `close-unit.ps1:163-169`'s
  `Save-Text` function was written and regression-tested (`test-kit.ps1:4047-4089`) specifically because
  the SAME bug (a hardcoded line ending fighting `.gitattributes`) bit that one call site. But `Save-Text`
  is local to `close-unit.ps1` - it is not a shared utility other scripts import, so the same class of bug
  is free to recur anywhere else a script builds a multi-line string and writes it. It already has: see
  Top Issues #1 and #3.
- **`ratchet.ps1` and `close-unit.ps1` are two different scripts implementing overlapping bookkeeping
  patterns** (both compute counts against `docs/`, both write JSON/text state) without sharing code - not
  wrong, but it is why the CRLF-writing bug had two independent occurrences instead of one.
- **`test-kit.ps1` at ~4,100 lines is itself the single largest file in the repo** and is entirely
  fixture-driven `Test-Case` blocks; no test helper library extracts the extremely repetitive
  `Set-Content ... -Encoding UTF8` fixture-scaffolding boilerplate (visible across hundreds of lines, e.g.
  `test-kit.ps1:1317-1974` repeats near-identical `CLAUDE.md`/`DESIGN.md`/`STORIES.md`/`TASKS.md` fixture
  setup dozens of times). This is a maintainability cost, not a correctness bug - each `Test-Case` is
  independently readable, which is presumably the deliberate tradeoff (a shared fixture builder would make
  each test shorter but harder to read standalone).
- **No test brittleness or dead code found** in the scripts read for this pass. `dad-loopguard.ps1`,
  `dad-guard.ps1`, `ratchet.ps1`, `recover-lost.ps1` are all commented with the specific real incident that
  motivated them (e.g. `ratchet.ps1:7-16`, `dad-guard.ps1`'s own header) - an unusually well-grounded
  commenting convention that makes this an easier codebase to assess than most.
- **Self-hosting gap**: this kit's own `CLAUDE.md` does not conform to the shape its own `close-unit.ps1`
  expects (Top Issue #2) - a genuine "physician, heal thyself" gap, low effort to close.

## Top issues (prioritized)

### 1. [P1 x S] `api-surface.ps1:64` hardcodes CRLF, silently reproducing the exact bug class S4/T4.1 just fixed - confirmed currently failing the gate
**Evidence**: `Add-SourceFiles` (`api-surface.ps1:39-65`) is called unconditionally on every regeneration of
`docs\API-SURFACE.md` (`api-surface.ps1:116`, and again via `-AnnotateFiles` at `api-surface.ps1:69`), and
writes the whole file back with `[System.IO.File]::WriteAllText($surfaceFile, (($lines -join "`r`n") +
"`r`n"), ...)` (`api-surface.ps1:64`) - a hardcoded CRLF into a file that lives under `docs/` and is
therefore governed by `.gitattributes:18`'s `* text=auto eol=lf`. I reproduced this live: the current
working-tree `docs/API-SURFACE.md` has 7,786 CRLF sequences, and running `test-kit.ps1 -SkipBuild` right
now fails its line-ending gate on exactly this file (`test-kit.ps1:387-415`'s assertion, output: "files
whose line endings do not match .gitattributes: API-SURFACE.md is CRLF but should be LF"). Because the file
is currently untracked (`git status` shows it as untracked, never committed to this repo per `git log --all
-- docs/API-SURFACE.md` returning nothing), `git status`/`git diff` show nothing wrong today - but the
moment `close-unit.ps1` runs `git add -A` (`close-unit.ps1:456`), git's `eol=lf` clean filter will
normalize the STAGED blob to LF while leaving the WORKING-TREE copy CRLF, reproducing invisibly-to-git-diff
exactly the masking mechanism `close-unit.ps1:164-167`'s comment describes for the bug S4/T4.1 already
fixed once (commit 9be3aec).
**Why it matters**: `close-unit.ps1:265-271` regenerates `docs\API-SURFACE.md` via this exact function
after EVERY successful build, on EVERY project, as part of the normal `/build` loop - so this is not a
one-off, it is the default path, and it re-breaks the validation gate every time it runs on the kit's own
self-hosted repo (or any project whose `.gitattributes` sets `eol=lf` for `.md`).
**Fix sketch**: change `api-surface.ps1:64` to match `close-unit.ps1:168`'s pattern -
`(($lines -join "`n") + "`n")` instead of `` `r`n ``. One-line fix, add a `Test-Case` mirroring
`test-kit.ps1:4047` ("close-unit writes TASKS.md/STORIES.md back as LF") but for `api-surface.ps1
-AnnotateFiles` regenerating a CRLF fixture into LF.
**Judged against**: `.gitattributes:1-18` (the kit's own stated rule) and `CLAUDE.md`'s validation-gate
contract ("must print `0 failed`" - `CLAUDE.md:30`), which is not currently true.

### 2. [P2 x S] `close-unit.ps1` cannot find a build command in the kit's OWN `CLAUDE.md` - every close-unit run against this repo skips build verification
**Evidence**: `close-unit.ps1:44-52`'s `Get-ClaudeCommand` looks for a line matching
`^\s*-\s*\*{0,2}Build\*{0,2}\s*:\s*` (i.e. a bullet whose LABEL is literally "Build", not heading-dependent
- it scans the whole raw file text, not a specific `##` section). This kit's own `CLAUDE.md:21-23` has a
`## Build` heading but the bullet under it reads `- C# server: \`dotnet build ...\`` - the label is "C#
server", not "Build", so the regex never matches and `Get-ClaudeCommand 'Build'` returns `""`. This is
exactly the WARNING every close-unit run in today's session printed (per the assessment brief) and is
reproducible by inspection alone: `test-kit.ps1`'s own fixtures always use the literal shape `- Build:
\`<cmd>\`` under a `## Build / test` heading (e.g. `test-kit.ps1:1317,1737,3701`) - the kit's own file was
never made to match that shape, and no `test-kit.ps1` fixture checks the kit's OWN root `CLAUDE.md` against
this contract (all fixtures are synthetic temp-dir projects).
**Why it matters**: every task/story closed against this repo (T4.1-T5.1, S4, S5 today) closes WITHOUT the
build verification `close-unit.ps1:229-233` is designed to provide - the same gate that catches a broken
build before it gets ticked and committed (`close-unit.ps1:210-212`'s own stated rationale: "a project once
had 5 stories marked DONE... while `dotnet build` failed"). The kit is currently exempting itself from its
own core safety mechanism.
**Fix sketch (recommended, S effort, low risk)**: add a literal bullet under `CLAUDE.md`'s `## Build`
heading: `` - Build: `dotnet build local-tools\local-tools.csproj -c Release` `` (keep the existing
explanatory line too). This alone restores build-level verification with NO side effect on story-level test
gating, because `close-unit.ps1:277-279` only WARNS (does not block) when no `Test:` bullet is found.
**Caution on the natural next step**: do NOT also add a literal `- Test: \`.\test-kit.ps1\`` bullet without
first addressing the 2 non-environmental-known failures, because `close-unit.ps1:284-296` would then BLOCK
every story close on this repo on a nonzero exit code from `test-kit.ps1` (which currently fails on 3
things, one newly real per #1 above) - that decision (wire `Test:` now vs. after cleanup, and whether to
filter environment-only failures) is a human call, not mine to make unilaterally.
**Judged against**: `close-unit.ps1:210-212`'s own documented purpose, and `CLAUDE.md`'s own "## Build"
heading, which currently does not deliver what the script that reads it expects.

### 3. [P3 x S] `ratchet.ps1:145` writes its JSON baseline with platform-default (CRLF) line endings - same bug PATTERN as #1, different file, currently masked only because the target dir is gitignored
**Evidence**: `ratchet.ps1:145` - `[System.IO.File]::WriteAllText($baselineFile, (($current |
ConvertTo-Json)), (New-Object System.Text.UTF8Encoding($false)))` - passes `ConvertTo-Json`'s output
straight through with no newline normalization. I confirmed `ConvertTo-Json` on this machine's Windows
PowerShell emits `\r\n` (a trivial repro: hashtable -> `ConvertTo-Json` -> 3 CRLF sequences in a 2-key
object). The target, `.claude\.dad-ratchet.json` (`ratchet.ps1:48`), is covered by the repo's own
`.gitignore:21` (`.claude/`), so unlike #1 this file is NEVER committed and therefore never subject to
`.gitattributes`' clean-filter masking on a real commit - but `test-kit.ps1:397-398`'s line-ending scan
walks the raw filesystem (`Get-ChildItem $kit -Recurse -File -Include *.ps1,*.cmd,*.md,*.json,*.cs`,
excluding only `_tempReference|bin|obj|\.git|node_modules|examples`) and does NOT exclude `.claude\` the
way it excludes `.git\` - so any time this file exists with CRLF content, the SAME `test-kit.ps1` gate that
caught #1 would flag it too. This matches the session's reported symptom exactly (manual deletion needed
for a clean gate reading), even though `.dad-ratchet.json` does not currently exist in the tree (it was
deleted during today's session and no `close-unit -Update` has re-run since).
**Is it the same root cause as #1?** Same PATTERN (a script builds text with a platform/library-default
newline and writes it verbatim, ignoring the kit's LF convention), but a DISTINCT instance/location and a
distinct blast radius: #1 corrupts a file that IS meant to be committed and IS governed by
`.gitattributes`; this one corrupts a purely-internal, gitignored bookkeeping file that no other tool reads
except `ratchet.ps1` itself round-tripping via `ConvertFrom-Json` (`ratchet.ps1:157`), so functionally nothing
breaks except `test-kit.ps1`'s own overly-broad scan. Two independent instances of the same missing
convention (no shared "write LF text" helper - see Implementation section) is worth noting as a pattern,
not "one bug, fixed twice."
**Fix sketch - two independent, non-conflicting options**:
  (a) **Narrow the test's scope** (arguably the correct root fix): exclude `.claude` from
  `test-kit.ps1:398`'s exclusion regex, matching the kit's own stated philosophy elsewhere in the suite
  ("scaffold and upgrade ignore .claude/ (agent worktrees are not source)" - a passing `test-kit.ps1`
  `Test-Case` name already asserts this for scaffold/upgrade). A gitignored runtime directory should not be
  part of a "does the KIT'S SOURCE obey its own conventions" gate.
  (b) **Defensive normalization**: change `ratchet.ps1:145` to join on `` `n `` like `close-unit.ps1:168`
  does, for consistency even though nothing currently depends on it.
  Recommend doing (a) as the primary fix (it is the actual scope bug - a source-hygiene test should not
  scan non-source runtime state) and (b) opportunistically since it is a one-line change once you are
  editing the file anyway.
**Judged against**: `.gitignore:21` (`.claude/` is explicitly non-source) and the suite's own existing
precedent for treating `.claude/` as excluded runtime state.

### 4. [P3 x S] `test-kit.ps1:446`'s python-availability check treats a Windows Store app-execution-alias stub as "python is installed," turning an environment quirk into a red test
**Evidence**: `test-kit.ps1:445-450` gates on `Get-Command python -ErrorAction SilentlyContinue`, which
finds `C:\Users\...\AppData\Local\Microsoft\WindowsApps\python.exe` (the Store-install shim) even when no
real interpreter is present - reproduced directly: `python --version` on this machine prints "Python was
not found; run without arguments to install from the Microsoft Store..." and exits 49, which
`test-kit.ps1`'s `Assert ($LASTEXITCODE -eq 0)` then reports as `"voice.py failed to compile"` - a
misleading failure message for what is actually "no python here."
**Why it matters**: minor - this is a correctly-labeled "known pre-existing failure" per the assessment
brief, and does not block anything. But the error message actively misdirects (looks like a syntax error in
`voice.py`, not an environment gap), costing debugging time for anyone hitting it fresh.
**Fix sketch**: before the `foreach`, run `python --version 2>$null; if ($LASTEXITCODE -ne 0) { return }`
(mirroring the "optional on CI" comment's intent) so the stub is treated the same as "no python."
**Judged against**: `test-kit.ps1:446`'s own comment ("optional on CI") - the check's intent already
excludes "no python," it just does not detect the Store-stub case of "no python."

### 5. [P3 x L] No shared "write LF text, no BOM" helper exists kit-wide - convention is enforced by test-kit.ps1's scan after the fact, not by a single reusable function
**Evidence**: 15+ distinct `[System.IO.File]::WriteAllText(...)` call sites across
`close-unit.ps1:168,545,559`, `ratchet.ps1:145`, `api-surface.ps1:64`, `doc-stats.ps1:657`,
`recover-lost.ps1:187`, `install.ps1:27`, `new-project.ps1:50,60,87,100`, `upgrade-project.ps1:55,74,102,
227,229`, `uninstall.ps1:71,128`, `sync-models.ps1:68`, each independently choosing UTF8-no-BOM encoding
(correctly, per `CLAUDE.md:44`) but each independently deciding its own line-ending join (some `` `n ``,
some `` `r`n `` explicitly, some passing through `ConvertTo-Json`'s platform default unexamined). This is
the root reason the SAME bug class (#1, #3, and the already-fixed `close-unit.ps1` `Save-Text` bug) has
appeared three times: there is no single function a new script would call that already gets this right.
**Why it matters**: this is not urgent (only 2 of ~18 call sites are currently mis-written, per this pass),
but it is the underlying reason the bug recurs, and `test-kit.ps1`'s scan is a detection net, not a
prevention mechanism - it only catches the drift after it's written into a file already in the scanned
tree, and (per #3) only for tracked-shaped paths it remembers to scan.
**Fix sketch**: extract `close-unit.ps1:163-169`'s `Save-Text` into a small shared script (e.g.
`lib\text-io.ps1`, dot-sourced) taking a `-Crlf` switch defaulting to `$false`, and migrate the two
currently-wrong call sites (#1, #3) plus `recover-lost.ps1:187` and `doc-stats.ps1:657` (both currently
explicit `` `r`n `` into `.gitattributes`-governed `.md` paths, not independently verified as currently
broken in this pass but sharing the identical risk shape) onto it. This is an L-effort item only because it
touches ~10 files for full consistency; a partial fix (just #1 and #3) is S-effort and covers the two
CONFIRMED live issues.
**Judged against**: `.gitattributes:1-16`'s own stated rationale for why this file exists at all ("A
'line-ending style' setting in the kit could not have prevented any of it... this is where the rule
lives") - the rule lives in `.gitattributes`, but nothing enforces scripts read it before they write.

## Migration / rewrite options

This is a health assessment of a young, actively-maintained kit (103 commits, current session literally
closing stories against it) with a strong existing test gate (138/141 passing, failures are two
environment artifacts and one confirmed one-line bug) and an unusually well-documented "why" for nearly
every non-obvious piece of logic. Nothing here rises to a re-host or rewrite conversation. The options are:

1. **Fix inline now (recommended for #1 and #2)** - both are single-line/single-bullet changes with a clear
   regression-test pattern already established in this exact codebase (`test-kit.ps1:4047-4089` for #1's
   sibling bug). Effort: under an hour combined, including a new `Test-Case` for #1.
2. **File as a story/task and route through `/build`** - if the human prefers the normal
   dev-agent/qa-agent/close-unit loop over a direct edit, per `CLAUDE.md`'s working agreement. Given #1 is
   currently red on the actual gate, this is arguably higher priority than typical backlog grooming.
3. **Defer #3 and #5** - #3 has zero functional impact today (no file currently exists to trip it) and #5 is
   a larger refactor with no urgent forcing function; both are reasonable to batch into a future
   `/retro`-driven convention pass (per R27, `docs/DESIGN.md:178-188`) rather than fixed ad hoc.
4. **#4 is optional polish** - only worth doing if this machine's python-stub environment is representative
   of other contributors' machines; otherwise it is a one-machine annoyance, not a kit defect.

The human call is: fix #1/#2 now (small, evidenced, low-risk) vs. batch everything (including #1) into the
next `/build` or `/retro` cycle. Given #1 is an ACTIVE gate failure that will re-fire on the next
`close-unit` run against this repo, I would lean toward fixing it before the next unit closes here - but
that prioritization judgment is the human's to make, not mine.
